Workshop core SvelteKit principles woensdag 30-09

Reactivity

  • Reactivity gebeurt client side en is een extra laag.
  • Eerst zorg je dat alles goed werkt op de server. Daarna verbeter je het met Progressive Enhancement (PE).
  • Met client side komt de reactivity erbovenop.

Eventlisteners vs. reactivity

  • Eventlisteners (die kennen we al): je legt stap voor stap vast wat de browser moet doen.
  • Reactivity doet hetzelfde, maar hier bepaalt de data wat er gebeurt.
  • Onder water gebruikt Svelte dus ook eventlisteners.

Runes

Runes zijn speciale symbolen. Ze beginnen met een $.

$props()

  • De server stuurt data, en het page component krijgt die data binnen.
  • Brengt de server nieuwe data naar het page component, dan veranderen alle variabelen automatisch mee.
  • Props kun je ook van een parent component naar een child component doorgeven.
  • Verandert de data in het parent component, dan verandert die in het child component ook.

Aanvulling: de server "exporteert" de data via een load-functie, bijvoorbeeld in +page.server.js. Wat die functie teruggeeft, komt in +page.svelte binnen als data:

let { data } = $props();

Bron: $props en load

$state()

  • Gebruik je voor data die kan veranderen.
  • Voorbeeld: let count = $state(0);. Het getal tussen de haakjes is de startwaarde (hier 0), en count gebruik je in de template.

Bron: $state

$derived()

  • Gebruik je voor een waarde die je afleidt uit de originele data, bijvoorbeeld de waarde x 2.
  • Dit hebben we al gebruikt in de progress bar.

Aanvulling: let double = $derived(count * 2);. Verandert count, dan rekent Svelte double automatisch opnieuw uit.

Bron: $derived

$effect()

  • Dit is de laatste rune.
  • Hij is voor zogenaamde side effects: acties die niet in de template thuishoren.
  • De effect rune werkt alleen client side.

Aanvulling: zo werkt $effect

  • Wanneer draait hij? Eerst nadat het component in de DOM staat (gemount is). Daarna elke keer als een $state- of $derived-waarde verandert die je binnen het effect leest.
  • Hoe weet hij waar hij op moet letten? Dat hoef je niet op te geven. Svelte kijkt zelf welke reactieve waarden je in het effect gebruikt. Dat heten de dependencies.
  • Waarom alleen client side? Op de server wordt alleen HTML gemaakt. Er is daar geen browser en geen DOM, dus effects slaan de server over.
  • Opruimen: geef je in het effect een functie terug (return () => { ... }), dan draait die net voordat het effect opnieuw draait en wanneer het component verdwijnt. Handig om bijvoorbeeld een setInterval weer te stoppen met clearInterval.
  • Voorbeelden van side effects: document.title aanpassen, tekenen op een <canvas>, een timer (setInterval) of een externe library aansturen.
  • Let op: gebruik $effect niet om een waarde uit te rekenen uit andere state. Daarvoor is $derived. De Svelte-docs raden aan om $effect spaarzaam te gebruiken.
let count = $state(0);                        // waarde die kan veranderen, start op 0

$effect(() => {                               // draait in de browser na het mounten
  document.title = `Teller: ${count}`;        // leest count, dus draait opnieuw als count verandert
});

Het tabblad van de browser hoort niet bij de template van je component. Daarom is dit een side effect.

Bron: $effect

Hydration

  • Tijdens hydration gebruikt SvelteKit de DOM API en de Events API om de bestaande HTML van de server interactief en reactief te maken.
  • Na hydration regelen de History API en de Fetch API de navigatie, en dat gebeurt allemaal client side.
  • Wanneer Svelte een project laadt, worden de JS packages ingeladen.

CSR aan of uit

export const csr = true;
  • Met deze regel zeg je: doe dit client side.
  • Je kunt hem ook op false zetten, dan gebeurt alles server side.
  • Dit bepaalt of er wel of niet gehydrateerd wordt.

Aanvulling: deze regel zet je niet in een willekeurig JS-bestand. Hij hoort in een +page.js, +page.server.js, +layout.js of +layout.server.js. In een layout geldt hij ook voor alle pagina's daaronder.

Bron: page options: csr
